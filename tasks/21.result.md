## TASK 21C: confirmed secret leak fix (edit rejection-and-retry path)

### Root cause
`packages/fixer/edits.py` `apply_edits()`: when an edit's `find` text occurred 0 times, the code ran
`difflib.get_close_matches()` against the WHOLE unredacted source file (`file_text.splitlines()`)
and embedded up to 3 fuzzy-matched source lines (each truncated to 200 chars) into the rejection
message `f"edit {idx}: find text occurs 0 times. candidates: {cand_text}"`. `packages/fixer/patch_gen.py`
`generate_patch_edits()` then forwarded `apply_res.error` verbatim as retry feedback to the model
(`user += f"\n\nYour previous attempt was rejected: {feedback}\nTry again."`). A `find` near-matching a
line containing a secret caused that unredacted secret line to leak into the retry request and into
`PatchGenResult.reasons` (which flow into ladder escalation explanations and the fix report's
`patch_reasons`).

### Fix (packages/fixer/edits.py only)
Replaced all raw source-derived content in rejection diagnostics with safe structured reason codes:
- `SEARCH_BLOCK_NOT_FOUND: edit N: find text occurs 0 times` (no candidate lines, no source text)
- `AMBIGUOUS_SEARCH_BLOCK: edit N: find text occurs M times (ambiguous)`
- `INVALID_EDIT_TARGET: ...` for file-not-allowed / unsafe path / not in original files
- `EDIT_VALIDATION_FAILED: diff too large (N lines, max M)`
No `find`/`replace` strings, no source excerpts, no candidate lines, no unredacted exception messages
appear in any rejection diagnostic. `patch_gen.py` needed no change — it already forwards
`apply_res.error` verbatim, which is now safe. Verified exposure points: `ladder.py:87`
(escalation explanation from `patch.reasons`), `run_fix_batch.py` report field `patch_reasons`; no
logging of `apply_res.error`; `ModelResult.error` is documented as redacted.

### Safe diagnostic design
Deterministic rejection preserved (exact-once `find`, all-or-nothing apply, bounded 3 attempts,
source immutable on failed edits, approval still required, independent verification unchanged).
The fix does NOT rely on regex key-format detection: arbitrary sensitive source content is excluded
by construction.

## TASK 21D: structured patch & security repair (DONE)

### Root cause
`packages/fixer/edits.py` `apply_edits()` built its unified diff by joining difflib output lines (produced with `keepends=True`, so each line already carries its `\n`) with `"\n".join(...)`, emitting a double newline between every line. The model-proposed patch was therefore malformed and `git apply` rejected it ("corrupt patch at line 11"). Additionally, when an edit's `find` text occurred 0 times, the applier ran `difflib.get_close_matches()` against the whole UNREDACTED source file and embedded up to 3 fuzzy-matched source lines into the rejection diagnostic; `patch_gen.generate_patch_edits()` forwarded that verbatim as retry feedback to the model, leaking arbitrary sensitive source content (API keys) into retry prompts and `PatchGenResult.reasons` (downstream into ladder escalation explanations and fix-report `patch_reasons`). Invalid-target diagnostics also interpolated the raw model-supplied file path.

### Fix (packages/fixer/edits.py only)
- Diff building: emit each difflib line terminated with the file's REAL line ending (`\r\n` for CRLF files, `\n` otherwise), joining directly (no extra newline). Adds the `\ No newline at end of file` marker when a file lacks a trailing newline. The diff now applies cleanly via `git apply`.
- Unsafe diagnostics: all rejection reasons are now safe structured codes — `SEARCH_BLOCK_NOT_FOUND`, `AMBIGUOUS_SEARCH_BLOCK`, `INVALID_EDIT_TARGET`, `EDIT_VALIDATION_FAILED` — with NO source text, no candidate lines, no find/replace strings, no unredacted exception text, and no model-supplied paths. `patch_gen.py` needed no change (it forwards `apply_res.error` verbatim, which is now safe).
- Added a try/except so unexpected validator errors return `EDIT_VALIDATION_FAILED` without leaking exception text.
