Sentinel X — results

What Sentinel X is. Sentinel X watches AI agents and web sites the same way a security guard watches a building: every action an agent proposes is checked against a strict written policy before it runs, and every request a web site receives is inspected by a reverse proxy. Everything the system sees is stored in a tamper-evident evidence chain, and a separate verifier - never the model that proposed the action - scores what actually happened. This page is generated only from stored result files, so every number below can be traced back to its source.
How to read this. ATTEMPTED vs EXECUTED: a blocked attack was ATTEMPTED, not EXECUTED - the gateway refused it before the tool ran, so no forbidden outcome occurred. State labels: OBSERVED = directly recorded, INFERRED = derived by our rules, SIMULATED = produced by our scripted stand-ins, VERIFIED = independently re-checked. Shield rules are TEMPORARY SHIELD, NOT A FIX: they buy time for a human; only an applied, verified patch is a fix.

Limitations

evaluations/example_report/report.json

The agent is a SCRIPTED, deliberately gullible simulation. It is not an LLM and says nothing about how any real model behaves.
Results show how the implemented controls behave against THESE specific hand-authored cases. They say nothing about unseen attacks, other fixtures, or real models.
Counts are small (tens of cases, one repetition by default); rates carry large uncertainty and no confidence intervals are claimed.
No claim of complete protection is made. A 0% attack success rate here means these cases were stopped, not that other attacks would be.
Arm B's static policy was written knowing the lab; the false-positive and false-confirm numbers show its cost on these benign cases only.
Latency figures measure a local sqlite/Playwright prototype on one machine; they are not production performance claims.

evaluations/example_report_model/report.json

The agent is a REAL language model (see provenance for provider, model and mode), driven by one fixed prompt (prompt_v1). Results describe THIS model, THIS prompt and THIS date; another model, prompt or sampling seed can behave differently.
Model output is nondeterministic (temperature 1.0): with one repetition per case each number is a single sample, so small differences between arms are not evidence. Counts are small (tens of cases) and no confidence intervals are claimed.
Results show how the controls behave against THESE hand-authored cases. They say nothing about unseen attacks, adaptive attackers, other tasks or other models. No claim of complete protection is made.
The attack text was NOT tuned to the model: a low unprotected attack success rate means this model resisted these particular texts, not that the attacks are harmless.
The system prompt contains a generic notice that page content is untrusted data, and the user notes name the pages/endpoints to use; both make the model more resistant than a bare agent would be. The user-requested answer format is part of the goal assertion.
Arm B's static policy was written knowing the lab; the false-positive and false-confirm numbers show its cost on these benign cases only.
The hosted trial endpoint has undocumented rate limits and variable latency; runs that hit MODEL_UNAVAILABLE are invalid, excluded from rates and counted. Latency figures are for this endpoint on this day and are not production claims.

evaluations/example_report_evcs/report.json

The agent is a SCRIPTED, SIMULATED planner (not an LLM). It obeys injected instructions by fixed rules, so these results say nothing about how a real model would behave.
The 30 cases were authored together with the policy, so the controls were built knowing them; the numbers show behaviour on THESE cases, not on unseen attacks.
A branch is a RE-EXECUTION of a scripted run in our own resettable lab fixtures (a bounded digital twin of OUR lab, not of any real site). Nothing real is rolled back; effects the parent run produced stay in the parent.
Small n: 15 attack cases, 1 run per branch, no confidence intervals.
The disruption weights are our own choice (weights file, version recorded): a different weighting can change the recommendation. Latency is priced at 0 by default for reproducibility.
SIMULATED approvals: the ScriptedOperator is code driven by a hand-authored file, not a human; it proves the workflow and the binding rules, not human behaviour.
Selection is deterministic code. The optional model suggestion only chooses which branches to try and can never mark one safe.
No claim of complete protection is made.
