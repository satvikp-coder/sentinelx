## 5. NVIDIA 404 investigation
The 4 invalid runs of `evaluations/runs/model-subset-1` (from the stored `MODEL_CALL` / `PLANNER_FAILED` events):

| Run | Error | Notes |
|---|---|---|
| B08 arm A | `HTTP 404: ` (empty body), 1 HTTP call, 4.5 s, no retry | 2 successful calls earlier in the same run |
| B02 arm A | `HTTP 404: ` (empty body), 3.5 s | 0 successful calls: the FIRST call failed |
| A06 arm B | `HTTP 404: ` (empty body), 0.27 s | 1 successful call earlier |
| B06 arm B | `per-run model call cap reached` | NOT a 404: 10 successful calls, then our own cap (10) stopped a looping model |

The three 404s happened within 14 seconds of each other (05:18:48-05:19:02 UTC), had **empty bodies and no request id**, and hit different sessions, one of them on its very first call, while the same URL and model name had worked before and worked right after. So: not a wrong path, not a wrong model name (both identical to successful calls), not a quota response (no 429 / Retry-After / body). It looks like a short transient gateway/routing glitch on the free trial endpoint.

Live probe (3 small calls, 30 s apart, no code changed): **3/3 returned HTTP 200** (2.3 s, 4.7 s, 1.2 s; `nvcf-status: fulfilled`). The 404 did not reproduce.

Conclusion: transient. The adapter treats every 4xx as an immediate non-retried `MODEL_UNAVAILABLE`, which cost 3 of 20 runs. For this endpoint a 404 with an empty body should be treated as retryable once or twice with backoff (see fix list). It does not change results already reported: those runs are listed as invalid and excluded.
