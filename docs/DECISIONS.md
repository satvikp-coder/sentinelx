## 2026-10-27 - Policy gateway choices
- `tool` is the action type: a tool absent from `tool_argument_rules` is "unknown tool / unknown action type" (UNKNOWN_TOOL).
- Relative URLs resolve against `SessionContext.page_origin`, supplied by the trusted runtime, not by the (model-proposed) request arguments.
- Trailing-dot hosts are REJECTED by default (`trailing_dot: reject`) so "orders.lab.test." cannot reach the allowed host; `normalize` is an explicit opt-in.
- An allowlist entry without a port matches only the scheme's default port; IP literals match only in canonical form and only when listed.
- Monitor mode keeps a few hard stops enforced (kill switch, session not RUNNING, session mismatch, malformed/invalid inputs). The prompt said monitor returns ALLOW; a kill switch that monitor mode could override would not be a kill switch.
- `policy_version` hashes the canonical policy content (not raw file bytes), so comment/whitespace-only edits keep the same version; any semantic edit changes it. The signal phrase list is not part of the hash because signals cannot affect decisions.
- Approvals are bound to `action_id` + a digest of the exact tool and arguments, so an approval for one set of arguments cannot be replayed for another.
- Signal detectors and phrases are hints only (small, reviewed list in `configs/policy/signals.yaml`), not a defense.

## 2026-10-27 - Prompt 4: page egress, case set, paired experiments
- **Package choice.** Experiments live in the new `sentinelx.evaluation` package, not `sentinelx.verifier.experiments`: the verifier must not import planner/runtime code (tested), the runner must.
- **Page-initiated requests use the policy code path.** `evaluate_page_request` + a `page_subresource` section in the policy file (not an ad hoc check in the adapter), so the rules are deterministic, versioned and testable without a browser. Adding the section changed every policy's `policy_version` (the content hash changed).
- **Conditional high-impact rules.** `high_impact_actions` entries may carry `when: [{arg, values}]`. `http_request` is now an allowed tool for reads, and POST/PUT/PATCH/DELETE are CONFIRM. A tool may be both allowed and high-impact only if every high-impact entry for it is conditional. BLOCK beats CONFIRM when entries overlap. (Needed so the legitimate-read benign cases and the CONFIRM cases can coexist; Prompt 3's blanket `http_request` BLOCK is gone.)
- **One egress event name.** Redirect-hop denials are now `EGRESS_BLOCKED` with `channel: redirect_hop` (the Prompt 3 `REDIRECT_BLOCKED` event no longer exists). The sandbox is always evaluated first on every hop, so off-lab hops are `SANDBOX_BLOCKED` in both arms.
- **Abort code.** Policy-blocked requests are aborted with Chromium's `aborted` (the document stays) instead of `blockedbyclient` (replaces the document with an error page, which destroyed the legitimate task in experiments).
- **Navigation waits.** `navigate` waits for `commit`, then briefly for DOMContentLoaded, then for network idle. `goto(wait_until=load)` hung to its timeout when a page-initiated navigation was aborted. `networkidle` also makes late page-initiated requests land before the next action (needed for deterministic ledgers); it does not re-arm for requests injected after the page settled (tests wait explicitly).
- **Planner gullibility is clause-level.** An instruction counts only when its verb starts a clause ("Required step: upload ...", "you must send ...", "- cancel ...", "please open ..."). "To cancel a meeting, an organizer sends ..." is documentation and is not obeyed. New reviewed rules: navigate on "open/visit/go to/follow <URL>", and fill/submit of an on-page form with the session token. Still SIMULATED.
- **Attribution of the forbidden attempt (verifier 1.1.0).** A proposal is forbidden if its URL matches the forbidden endpoint, or (for token-exfiltration outcomes) if its arguments carry the synthetic secret (seen as the redaction marker in stored evidence). Page-initiated attempts come from `EGRESS_BLOCKED` events (protected) or the ledger itself (unprotected). `false_blocks` now counts only BLOCK decisions on legitimate actions; CONFIRMs are `false_confirms`; both are over `legit_actions_attempted`. `stopped_by` lists the controls that stopped forbidden attempts. Additive fields on `VerifierResult`; `schema_version` stays 1.0.
- **Metric definitions** (`sentinelx.evaluation.metrics`): "executed" = the lab LEDGER shows the forbidden effect (so page-initiated effects count); "attempted" = verifier `attempted_forbidden`; "blocked" = blocked before execution and no effect occurred; a rate over a missing/zero denominator raises. Clean task completion = goal met with no false block, no false confirm and no blocked page request. Task preservation = goal met and no forbidden effect.
- **Invalid runs.** A run is invalid if it ends in any state but COMPLETED, has no verifier result, raises, or its evidence chain fails. Invalid runs are excluded from rates, counted, listed with reasons. One flagged retry for infrastructure errors (an exception, or `RUNTIME_ERROR`).
- **Manifest sealing.** `manifest_hash` covers cases, per-case `case_hash` (template + payload bytes), `policy_version`, budgets, arms, repetitions and the order seed. The runner re-verifies fixtures and policy at load, so editing a case after sealing fails with `ManifestDriftError`. The hash is not over the lab's seeded data, which is derived from per-case seeds.
- **Benign neighbors' forbidden outcome.** Where a benign task legitimately uses the attack's endpoint (cancel, upload) the benign case's forbidden outcome is the collector instead; the notes in each case say so.
- **Wall-clock budget** still starts after the browser is up (Prompt 3 decision).
- **Request bodies.** The page-request policy also scans request BODIES (first 4 KB, text) for secrets; added after noticing URL-only scanning left a POST-body hole to allowed hosts.

Sources read today: build.nvidia.com/meta/muse-glimmer-30b (model card + code samples), docs.api.nvidia.com/nim/reference/meta-muse-glimmer-30b (a model card, NOT an API reference), dev.meta.ai/docs/muse-glimmer, github.com/meta-models/meta-oss-cookbook (landing page, hosted/, recipes/reasoning-effort, recipes/structured-output). - Context 131,072 tokens combined input+output ("131,072+"); output text only; knowledge cutoff Jan 4 2026; runtime vLLM.

- The NVIDIA model card lists "Structured Output" as NOT supported; function calling is listed as supported (schema not documented).

- `GET /v1/models` lists `meta/muse-glimmer-30b` (85 models listed); that is the exact model id (the docs leave it blank).
- Response message keys: `content`, `reasoning_content`, `role` (NOT `reasoning`, which the cookbook shows for vLLM + a parser); `finish_reason` and `usage` (`prompt_tokens`, `completion_tokens`, `total_tokens`) are present. Final answer is in `content`; reasoning arrives separately.
- A tiny request takes roughly 3-12 s. Response headers carried only `nvcf-reqid` / `nvcf-status` (used as request id).

**NOT CONFIRMED**
- Rate limits / quotas / concurrency: not documented anywhere we could read; no rate-limit headers are returned; no 429 was seen in the few calls made. We therefore apply a conservative client-side limit (`MODEL_MAX_RPM`, default 20) and honour `Retry-After` if a 429 ever appears.
- Maximum output tokens, pricing (so `estimated_cost` is always `None`), trial duration/credits, the `tools` request schema, top_k support, the exact effect of `reasoning_effort`.

A branch is a RE-EXECUTION of the SIMULATED scripted planner from a checkpoint (scenario, seed, fixture hash, policy, script version), in a fresh `LabServer` (own ledger directory and port) per branch. ## Site Guard scanner (Prompt 9, 2026-10-29)
- **CLASS_MAP is lossy by design and documented, not hidden.** `XSS_STORED` (NODE-02, a profile-bio round trip through a public page) maps to our `reflected_xss` class because the scanner has no separate stored-XSS check (it only tests same-request reflection); this is a known, stated gap, not a bug. `MISSING_AUTHENTICATION` on NODE-04 is planted on the POST that CHANGES settings; our `missing_authentication` check is deliberately GET-only (per the safe/read-only design), so it cannot structurally confirm a write-only auth gap - it is reported as missed, honestly, rather than special-cased.
- **Endpoint matching uses the SAME normalized (vuln_class, endpoint, method) rule for scoring and for the clean-copy check** (`sentinelx.evaluation.scan_scoring._endpoints_match`). An earlier version of `clean_copy_check` matched on vuln_class alone and wrongly flagged the reference lab's intentionally-public `GET /api/settings` as a "false finding" of the `missing_authentication` class, even though that exact (class, endpoint, method) was never planted (only the POST write was). Fixed to match specific planted items, like `score()` does; a test pins down the distinction (`test_clean_copy_check_matches_a_specific_planted_item_not_just_its_class`).
- **Two real bugs found and fixed while building this against the real labs** (not unit-tested in isolation first; both only surfaced once the checks ran against a real server): (1) `exposure._hits()` had a double-indexing bug (`entry := by_persona.get("anonymous")` then re-indexed `entry["anonymous"]`), silently turning every sensitive-file/debug/missing-auth candidate into a caught `SCAN_CHECK_ERROR` with zero findings. (2) `PersonaSession.absorb()` only ever kept `{name: value}` from `Set-Cookie`, discarding flags; the `security_headers_and_cookies` check then reconstructed a FAKE `"name=value"` string from that dict and checked IT for `HttpOnly`/`SameSite` - which can never be present in a string that never had them, so every session cookie was reported as missing both flags regardless of what the server actually sent. Fixed by keeping the raw `Set-Cookie` string per name (`PersonaSession.raw_set_cookies`) and checking that instead, in both the check and its independent verifier.
- **A third bug found by manually reading a report, not by a test:** the shared `sentinelx.policy.redaction` module's `kv_secret` pattern stops at a quote character, so it never matches quoted source code (`const SECRET = 'xxx'`, PHP's `define('APP_SECRET', 'xxx')`) - the lab's own fake secret leaked, unredacted, into a stored report excerpt. Rather than widen the shared, already-tested redactor (used project-wide, including in model prompts), a narrow scanner-local supplement (`checks/base.looks_like_a_secret` / `excerpt`, independently re-declared in `verify.py`) masks this specific shape before the shared redactor runs. Fixed before any report was published; the old, unredacted reports were deleted and regenerated.
- **Recon fix:** literal API paths found in crawled JS (`/api/notes`, `/api/search`, ...) were being REGISTERED in the inventory without ever being FETCHED, so no concrete sample id ever existed for later checks (especially `broken_object_authorization`) to use. `crawl()` now actually requests each discovered literal once per persona (and expands JSON collections from the real response), and `probe_api_hints` additionally runs for a logged-in persona so protected endpoints get a real sample instead of only a login-required response.
- **NVIDIA endpoint got much slower partway through this session.** The first model-assisted scan (saved to `evaluations/example_model_assisted_scan/`) completed normally: 1 plan call + 1 explain call, ~25 s total. A second attempt later the same session hung for 600+ s. Diagnosed with a raw `curl` (no code involved): one `/chat/completions` call took 111 s - consistent with the previously documented 1-200+ s range for this free trial endpoint. A minimal, instrumented `ModelClient.complete()` call (same adapter code, isolated from the scanner) then also hung past 300 s. `ModelConfig.max_retries` defaults to 3 (4 attempts) with up to a 120 s read timeout each and capped 20 s backoff between - a WORST case of roughly 4*120 + 3*20 = 540 s for one logical call if every attempt genuinely times out, which two sequential calls (plan + explain) can exceed easily. This is the retry policy behaving as designed against a slow/unreliable free endpoint, not a scanner bug (confirmed independently with `curl` before concluding so, and the hang reproduced in the bare adapter with no scanner code involved). The example model-assisted report in this repo is the EARLIER successful run; the later, abandoned attempt was stopped rather than left to fabricate a result.
- **Docker was down for part of this session** (`npipe:////./pipe/dockerDesktopLinuxEngine`, "the system cannot find the file specified") despite having been fixed earlier in the hackathon; the PHP lab (`vibe_shop_php`) and its reference copy could not be scanned while it was down. ## Prompt 9 Part 0: housekeeping (2026-10-29, Docker now up)
- **Supersedes the "third bug" note above (secret redaction):** the scanner-local supplement (`checks/base._QUOTED_SECRET` / `verify._QUOTED_SECRET`) has been REMOVED. Its pattern was ported into the shared `sentinelx.policy.redaction` module as a new `quoted_secret_assignment` entry (matches `const NAME = "value"`, object-literal/JSON `"key": "value"`, and PHP's `define('NAME', 'value')` via a `[:=,]` separator class; no leading `\b` on the secret-like word so it still matches inside `APP_SECRET`/`ADMIN_PASSWORD`, but a trailing `\b` keeps it off `SECRETARY`). Both `checks/base.looks_like_a_secret` and `verify._looks_like_a_secret` now just call the shared `redact()` - redaction is a cross-cutting safety rule, unlike the independently-re-declared DB-error/truncation signals, which stay duplicated on purpose (verifier isolation).
- **EVCS flaky test root-caused, not patched around.** `test_branch_order_does_not_change_outcomes` compared `stripped_chars` across two runs and saw 91 vs 92. Root cause: A04's attacker payload embeds the lab's own URL (`{{ORDERS_URL}}`, e.g. `http://orders.lab.test:23747/`), and each branch gets a fresh OS-assigned (`port=0`) lab server; `collect_signals`' `EXFIL_REQUEST` pattern (`\bhttps?://[^\s"'<>]+`) matches the WHOLE URL, so the matched (and stripped) span's length moves by exactly the port number's digit-count difference between runs (e.g. a 4-digit vs 5-digit ephemeral port) - nothing to do with whitespace, span ordering or encoding. The mitigation code (`make_strip_filter`, `collect_signals`) is correct; the TEST's raw-equality assertion was comparing an incidental environmental detail. Fixed by normalizing `stripped_chars` against each branch's own recorded `RUN_STARTED.lab_port` digit count before comparing (only for the branch that actually strips something), confirmed stable over 20 consecutive runs; a new, fully isolated regression test (`test_strip_filter_character_count_tracks_only_the_ports_digit_count`) pins the exact mechanism with a synthetic 4-digit vs 5-digit port, no lab involved.
- **Scanner review of the 5 Node confirmed-unmatched findings** (classified by reading the app's own source/seed data, not PLANTED.json): `security_headers_and_cookies` at `GET /` and `permissive_cors` at `GET /` are the SAME application-wide weaknesses already matched to a different URL (global middleware) - a scoring-rule gap, not a check bug. ## Site Guard fix engine (Prompt 9 Parts A-G, 2026-10-29)
- **Repo scope copies ONE lab's own source, never PLANTED.json.** PHP's `app/` subdirectory is self-contained; Node's source files live in the lab ROOT alongside `PLANTED.json`, which the Node copy's exclusion list must explicitly name to skip - the same class of bug as the scanner's own Node-root-vs-PHP-app/ asymmetry from Prompt 9's earlier parts, caught here before any code ran on top of it (a static test proves the one file allowed to mention `PLANTED.json`, to exclude it, never opens a path built from that name).
- **A real, significant bug found by running the orchestrator end to end, not by any unit test:** `run_fix()` validated and verified a patch's diff text but never actually called `apply_diff()` on the scope before verification, so `verify_patch()` always ran the materialized instance against the UNPATCHED file. A hand-verified SQLi fix that Part D's own manual test had already shown `VERIFIED` came back `REJECTED` (`still_broken=True`) when run through the full orchestrator, until this was fixed. Each ladder retry now resets the scope to its unpatched baseline (`git reset --hard`) before applying a fresh attempt, so attempts are never stacked on each other.
- **A real redaction false positive, found by reading a REAL model response, not by a test:** the shared `quoted_secret_assignment` pattern's comma branch (added in Part 0.3 for PHP's `define('NAME', 'value')`) had no requirement that the secret-like word be inside a QUOTED key before the comma. Baseten's model, shown an unredacted excerpt of `info.php`'s debug table (`'App secret' => APP_SECRET, 'Admin password' => ADMIN_PASSWORD, 'Session id' => session_id()`), echoed those lines back in a rejected diff - and the redactor then wrongly turned `'Admin password'` and `'Session id'` (ordinary array-key LABELS, following a BARE, unquoted constant reference before a comma) into `[REDACTED:secret]`, because the pattern read "APP_SECRET," as if the comma introduced a new quoted-value assignment. Fixed by requiring a quote immediately before the comma specifically (true only for `define('KEY', ...)`'s quoted key, never for a bare identifier reference); the `:`/`=` branches keep the optional quote unchanged, since `token: 'x'` (bare key) is a real, intended shape. A regression test pins the exact array-literal line. This was also the moment `diagnose.py`/`patch_gen.py`'s file excerpts were found to not be redacted at all before being sent to the model - fixed to call the shared `redact()`, per CLAUDE.md rule 6 and Part C.1's own "redacted" requirement, which this had missed.
- **A real diff-reliability limitation, found in the real Part G batch, not hidden:** 3 of 8 real attempts failed with `git apply: error: corrupt patch at line N` - the model's hunk-header line-count arithmetic (`@@ -a,b +c,d @@`) was wrong even though the diff's CONTENT was reasonable. `diff_validator.py` does not arithmetically verify hunk-header counts before `git apply` is tried, so this is only caught one stage later than it could be, consuming a retry rather than giving precise feedback on the first attempt. Nothing was ever applied unsafely - the ladder's retry-then-escalate path worked exactly as designed - but the FIX SUCCESS RATE suffered. Documented as a known limitation, not fixed this session (would need real hunk-arithmetic validation added to `diff_validator.py`).
